# 14. Data Architecture

> **Status:** Living document
> **Version:** 1.0
> **Last Updated:** 2026-09-27

BOUND uses **local files only** — no database engine. This keeps it fully offline and easy to
deploy/demo. It is prototype-grade (broadcast-safe but not concurrent-write-safe at scale).

---

## 2. Encrypted document record

`storage/encrypted/DOC-XXX.json`:

```json
{
  "document_id": "DOC-001",
  "original_filename": "report.pdf",
  "original_extension": ".pdf",
  "content_type": "application/pdf",
  "sender_id": "ALICE",
  "document_hash": "<sha256 of plaintext>",
  "aes_nonce": "<b64, 12 bytes>",
  "ciphertext": "<b64 AES-256-GCM ct+tag>",
  "authorized_recipients": ["ALICE", "BOB"],
  "wrapped_keys": {
    "ALICE": {
      "kem_ciphertext": "<b64 ML-KEM ct>",
      "wrapped_key_nonce": "<b64>",
      "wrapped_key": "<b64 AES-GCM wrapped AES key>",
      "mlkem_variant": "768"
    },
    "BOB": { "…": "…" }
  },
  "created_at": "2026-09-14T10:30:00Z",
  "ciphertext_len": 123456,
  "original_len": 122880
}
```

- The plaintext is **never** stored.
- `send` validates recipients before writing; the whole record is written atomically? No —
  a plain `write_text` (prototype). See risk in `25`.

## 3. Identity registry

`backend/keys/recipients.json`:

```json
{
  "ALICE": {
    "recipient_id": "ALICE",
    "display_name": "Alice",
    "mlkem_pk_b64": "…",
    "mldsa_pk_b64": "…",
    "mldsa_variant": "65",
    "mlkem_variant": "768",
    "key_storage": "legacy",
    "created_at": "…"
  }
}
```

`backend/keys/<RID>_private.json` (encrypted accounts):

```json
{
  "user": "CAROL",
  "kdf": { "salt_b64": "…", "n": 16384, "r": 8, "p": 1 },
  "mlkem_sk_enc": { "nonce_b64": "…", "ct_b64": "…" },
  "mldsa_sk_enc": { "nonce_b64": "…", "ct_b64": "…" },
  "created_at": "…"
}
```

- Legacy demo accounts use plaintext `*_sk.b64` files.
- New accounts use scrypt + AES-256-GCM encrypted records.

## 4. Watermarked output naming

```text
{document_id}_{RECIPIENT}_{session_id}_{safe_stem}{suffix}
DOC-001_ALICE_SES-9F82A1_report.pdf
DOC-002_BOB_SES-1A2B3C_archive.xyz.zip
```

- `safe_stem` = original stem sanitized to `[A-Za-z0-9._-]`, max 40 chars.
- `suffix` is the **real** produced format: native extension, or `.zip` for container fallback.

## 5. Ledger files

| File | Format | Tracked? |
|---|---|---|
| `ledger/nodeN/ledger.jsonl` | one JSON entry per line | gitignored |
| `ledger/nodeN/checkpoints.jsonl` | one JSON checkpoint per line | gitignored |
| `ledger/nodeN/node_mldsa_pk.b64` | base64 public key | gitignored |
| `ledger/nodeN/node_mldsa_sk.b64` | base64 private key | gitignored |

`BOUND_LEDGER_ROOT` relocates this tree for LAN nodes.

## 6. Session & secret files

| File | Contents |
|---|---|
| `backend/data/sessions.json` | `{token: {user, created_at, expires_at}}` |
| `backend/data/download_secret.b64` | 32 random bytes, base64 |

Writes use tempfile + `os.replace` + `fsync` (atomic).

## 8. Data lifecycle & privacy

- Plaintext only ever exists transiently in memory / a download response.
- Watermarked copies persist under `storage/watermarked/` (demo convenience) — production
  would stream and/or delete after the TTL.
- The watermark ID is opaque; the ledger holds the recipient mapping.
- No data leaves the machine except in LAN mode to member nodes on the isolated network.

---

## 9. Known data-layer weaknesses

| Weakness | Impact | Label |
|---|---|---|
| Encrypted doc `write_text` is not atomic | crash mid-write could corrupt one record | 🔵 |
| Watermarked files retained indefinitely | disk growth / plaintext markings persist | 🟡 |
| No retention/rotation policy | prototype only | 🟡 |
| JSONL append is not lock-guarded across processes in local mode | fine for single-process demo | 🟡 |
| `sessions.json` holds all tokens server-side | fine for prototype | 🟡 |

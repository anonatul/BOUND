# 26. Rejected Ideas

> **Status:** Living document
> **Version:** 1.0
> **Last Updated:** 2026-09-27
> **Purpose:** show judges (and future teammates) that alternatives were considered and rejected for reasons, not by ignorance.**

---

## 1. Hyperledger Fabric / CometBFT / QBFT

**Rejected for the prototype.** Heavy infrastructure (Docker network, MSP, validators,
networking) with no requirement it uniquely satisfies. BOUND's custom ledger provides
tamper-evidence and no-single-admin on an air-gapped LAN with zero extra moving parts. The PS
explicitly permits the simpler fallback.

- 🟣 **Decision:** custom replicated signed ledger.
- 🟡 Revisit if a judge/organisation mandates a named DLT for procurement reasons.

## 2. Public blockchain (Ethereum etc.)

**Rejected.** Violates "offline / no public blockchain". Privacy of document hashes on a
public chain is also unacceptable for classified workflows.

## 3. DRM / screen-blocking

**Rejected.** DRM dies to a camera, breaks legitimate workflows, and solves *prevention*
rather than *attribution* — the exact framing the PS rejects.

## 4. Visible / static watermarking

**Rejected as the primary channel.** Identical for a group, easy to crop, visually intrusive.
Kept only as the human-visible "you got a copy" affordance in some products, not in BOUND.

## 5. ML-based / deep-learning watermarking

**Rejected for this prototype.** Adds model dependencies, training data, and
non-determinism; offers robustness gains only on camera/print paths that BOUND does not
claim anyway. DCT QIM is deterministic and sufficient.

## 6. DWT / SVD watermarks

**Rejected.** DWT needs wavelet/multi-level tuning; SVD is fragile under cropping and slower.
DCT QIM already survives the realistic threat (JPEG re-encode) and is simple to verify.

## 7. Encrypting the whole file with ML-KEM

**Rejected immediately.** KEMs encapsulate a fixed-size secret; they are not bulk ciphers.
`mlkem_encaps` is used only to wrap the AES key.

## 8. Implementing ML-KEM/ML-DSA ourselves

**Rejected.** The PS mandates established libraries. Rolling your own PQC is a security
anti-pattern. `pqcrypto` is used and the code fails loudly if it is absent.

## 9. RSA/ECDSA fallback when PQC is unavailable

**Rejected.** Would silently defeat the entire "post-quantum" requirement. The wrapper raises
instead.

## 10. Storing the recipient private key server-side in plaintext

**Rejected for new accounts.** New accounts use scrypt + AES-256-GCM encrypted key files.
Legacy `ALICE`/`BOB` plaintext keys remain only for demo compatibility and are flagged.

## 11. Calling the ledger "immutable" / "a blockchain"

**Rejected as wording.** Both are false and would be immediately attacked. The correct claim
is "tamper-evident, quorum-replicated, independently signed".

## 12. Electron / native default viewer (first cut)

**Rejected for the MVP.** A browser SPA is faster to demo and covers all required flows. The
PS lists Electron as an option, not a requirement. A hardened native viewer is future work.

## 13. Hiding limitations

**Rejected by principle.** The PS itself demands honesty; the README and this KB tag every
claim. Hiding limitations is the fastest way to lose a technical judge.

## 14. AI/NLP anywhere

**Rejected.** There is no prediction or language task in the core problem. Adding AI would be
buzzword-driven.

## 15. Per-recipient (not per-session) watermark

**Rejected as too weak.** It would leak which recipient but not which session, and repeated
decryptions would be indistinguishable. Session+nonce derivation is strictly better.

## 16. Putting identity inside the watermark

**Rejected on privacy grounds.** The artifact carries only an opaque 128-bit ID; the ledger
holds the mapping. This stops a leaked file alone from exposing a name.

## 17. TLS everywhere by default in LAN mode

**Rejected for demo simplicity**, with a clear recommendation to add a local self-signed CA
for any real deployment. The isolated router is the boundary in the demo.

## 1. Algorithm inventory

| Purpose | Algorithm | Standard | Parameters | Where |
|---|---|---|---|---|
| Key encapsulation | **ML-KEM-768** | NIST FIPS 203 (Aug 2024) | NIST Level 3 | `pqcrypto.kem.ml_kem_768` |
| Signatures | **ML-DSA-65** | NIST FIPS 204 (Aug 2024) | NIST Level 3 | `pqcrypto.sign.ml_dsa_65` |
| Symmetric AEAD | **AES-256-GCM** | NIST SP 800-38D | 256-bit key, 96-bit nonce | `cryptography` |
| Hash | **SHA-256** | FIPS 180-4 | 256-bit | stdlib `hashlib` |
| Key derivation | **scrypt** | RFC 7914 | n=2¹⁴, r=8, p=1, dklen=32 | stdlib `hashlib.scrypt` |
| Download token | **HMAC-SHA256** | RFC 2104 | 32-byte secret | stdlib `hmac` |
| Session tokens | `secrets.token_urlsafe(32)` | — | 256-bit | stdlib `secrets` |
| Node ID / session randomness | `os.urandom` / `uuid4` | — | 128-bit nonce | stdlib |

> Variants `ml_kem_512/1024` and `ml_dsa_44/87` are also wired in the wrapper; the
> prototype uses 768/65 everywhere.

## 2. Why hybrid encryption

Never encrypt a large file directly with a KEM.

```text
1. aes_key = random 256-bit
2. ciphertext = AES-256-GCM(aes_key, plaintext)
3. for each recipient:
      kem_ct, ss = ML-KEM-768.Encap(recipient_mlkem_pk)
      wrapped  = AES-256-GCM(ss, aes_key)
```

Rationale:
- KEMs encapsulate a **fixed-size shared secret**, not arbitrary data.
- AES-GCM is fast for large documents and authenticated.
- One ciphertext, N small wrapped keys → efficient broadcast.

- 🟣 **DECISION:** the AES key is wrapped with the raw 32-byte ML-KEM shared secret used
  directly as an AES-256-GCM key (`wrap_key_with_ss`), with the assert `len(ss)==32`.
  A production build would derive a wrapping key with a KDF; this is acceptable for a
  prototype because the shared secret is uniformly random.

## 3. ML-KEM-768 in code

`pqcrypto_wrapper.py`:

```python
def mlkem_keygen(variant="768") -> (pk, sk)
def mlkem_encaps(pk, variant="768") -> (ciphertext, shared_secret)
def mlkem_decaps(sk, ciphertext, variant="768") -> shared_secret
```

- `mlkem_decaps` returns exactly 32 bytes; `wrap_key_with_ss` asserts this.
- The variant is stored per wrapped key (`mlkem_variant`) so decryption uses the same set.

Reference sizes for ML-KEM-768 (FIPS 203):
- encapsulation key (public): **1,184 bytes**
- decapsulation key (private): **2,400 bytes**
- ciphertext: **1,088 bytes**
- shared secret: **32 bytes**

🔵 Sizes above are from the FIPS 203 standard; the code does not hardcode them (it uses the
library), but they are useful to quote in the pitch.

## 4. ML-DSA-65 in code

```python
def mldsa_keygen(variant="65") -> (pk, sk)
def mldsa_sign(sk, message, variant="65") -> signature
def mldsa_verify(pk, message, signature, variant="65") -> bool
```

Reference sizes for ML-DSA-65 (FIPS 204):
- public key: **1,952 bytes**
- private key: **4,032 bytes**
- signature: **3,309 bytes**

- ✅ `mldsa_verify` is real: it calls the library and returns `False` on any exception —
  never a faked `True`. `test_mldsa_modified_rejection` proves it rejects modified messages
  and modified signatures.

## 5. Canonical event signing

`forensic/events.py`:

```python
def canonical_serialize(event):
    return json.dumps(event, sort_keys=True, separators=(',', ':')).encode()
```

Event fields (in `create_decryption_event`):

```json
{
  "event_type": "DOCUMENT_DECRYPTED",
  "document_id": "DOC-001",
  "document_hash": "<sha256 hex>",
  "recipient_id": "ALICE",
  "session_id": "SES-9F82A1",
  "watermark_id": "WM-…",
  "nonce": "<32 hex chars>",
  "timestamp": "2026-09-14T10:30:00Z"
}
```

- Signing: `mldsa_sign(recipient_mldsa_sk, canonical_serialize(event))`.
- Verifying: use the `public_key_b64` stored **with the ledger entry** (or the registry),
  recompute the canonical bytes, and verify.
- Any change to any field → verification fails. ✅ tested.

- 🟣 **DECISION:** the ledger stores the recipient's public key with the entry so a record is
  self-contained and verifiable even if the identity registry later changes.

## 6. Private-key protection at rest

New accounts (`register_user`):

```text
salt = os.urandom(16)
derived = scrypt(passphrase, salt, n=2^14, r=8, p=1, dklen=32)
mlkem_sk_enc = AES-256-GCM(derived, mlkem_sk)   # nonce + ct
mldsa_sk_enc = AES-256-GCM(derived, mldsa_sk)   # nonce + ct
```

Stored in `backend/keys/<RID>_private.json`; only public keys go into `recipients.json`.

Unlock model:
- `unlock_user(rid, passphrase)` derives the key, decrypts both private keys, caches them
  **in memory for 30 minutes** (`UNLOCK_TTL_SECONDS`).
- `get_private_keys()` returns cached keys while unlocked, or derives them with a supplied
  passphrase, else raises `PermissionError("private key locked")`.

- 🔴 **Known weakness (state it):** after unlock, the server process holds decrypted private
  keys and produces the signature on the recipient's behalf. This weakens true
  non-repudiation. Real deployment needs client-side signing or a hardware key.

## 7. Sessions

`auth/service.py`:
- `login` → verify by unlocking, then issue `secrets.token_urlsafe(32)`.
- Sessions persist to `backend/data/sessions.json`; TTL `12h`; expired tokens pruned.
- Bearer dependencies in `auth/deps.py` → `get_current_user` (401) and
  `get_current_user_optional`.

## 8. Download tokens

`main.py`:
- Payload `{"f": filename, "r": recipient_id, "e": expiry}` → base64url.
- `sig = HMAC-SHA256(download_secret, body)`.
- Token valid for `10 min`; compared with `hmac.compare_digest`.
- The secret is generated once and stored in `backend/data/download_secret.b64`.
- A valid bearer session is also accepted.

## 9. What the cryptography does and does not prove

| Property | Proves | Does NOT prove |
|---|---|---|
| AES-GCM tag | ciphertext unmodified | who decrypted it |
| ML-KEM | only the recipient's key can recover the AES key | the recipient's intent |
| ML-DSA signature | the holder of the private key signed this event | a human personally acted |
| Ledger node signatures | a quorum of node keys signed the entry | the event is factually true |
| Watermark | a copy came from that session's rendering | the copy was not further transformed |

> **Golden sentence:** *"The signature proves control of a private key, not human action."*
> (This is exactly the PS's §6 limitation.)

## 10. Cryptographic non-goals

- No forward secrecy (long-lived recipient keys; no ratchet).
- No key rotation / revocation in the prototype.
- No threshold cryptography for node keys (each node has one full key).
- No zero-knowledge proofs.
- No HSM/TPM/Secure Enclave.

## 1. Primary user roles

| Role | In the app | What they do | What they need |
|---|---|---|---|
| **Sender / Owner** | `Files` page | Uploads a file, selects recipients, shares | Confidence the document is encrypted and access is controlled |
| **Recipient** | `Shared with me` | Unlocks keys, decrypts, downloads a marked copy | A usable copy in the **same format** as the original |
| **Investigator / Auditor** | `Verify` + `Audit` | Uploads a leaked artifact, reviews ledger | A clear, verifiable attribution and tamper evidence |
| **Witness node operator** | LAN mode, `start_node.sh/.ps1` | Runs one ledger node per device | Simple setup, key stays local, auto-join |
| **Administrator / Coordinator** | Backend host | Runs the coordinator, manages membership | No ability to forge history alone |
| **Judge / Evaluator** | `Security demos` + `Verify` | Tests claims live | Reproducible, honest, impressive evidence |

## 2. User stories

### Sender
- "As a sender I can upload any file type and pick recipients, and one ciphertext is stored."
- "As a sender I can see who I shared with and how many times they decrypted."
- "As a sender I can open a document and see every recorded decryption session."

### Recipient
- "As a recipient I can unlock my passphrase-protected key for a 30-minute session."
- "As a recipient I get a copy that opens normally and preserves the original format."
- "As a recipient PDF text is still selectable and searchable after watermarking."

### Investigator
- "As an investigator I can drag a leaked file of any supported type and get a verdict."
- "As an investigator I see the recipient, session, timestamp, signature validity and node quorum."
- "As an investigator I can see if the audit record was tampered with."

### Witness / Admin
- "As a witness I start one command and my device joins the ledger."
- "As a witness my private key never leaves my machine."
- "As an admin I cannot rewrite history even with file access, because I lack node keys."

## 3. Deployment personas

### 3.1 Single-machine demo
- One laptop, local ledger = 4 directories.
- Demo accounts `ALICE` / `BOB` (`demo12345`) plus self-registration.
- Use case: hackathon evaluation, offline demo on a laptop.

### 3.2 Air-gapped witness LAN (the target config)
- Coordinator laptop + N witness laptops on a router with no uplink.
- Each witness runs `scripts/start_node.sh`.
- Quorum = strict majority of joined devices.
- Use case: the configuration intended to satisfy "no single administrator".

### 3.3 Organisational (future)
- Sender workstation, recipient clients with local key agents, witness nodes in separate
  security domains, hardware keys/HSMs, real viewer.
- Use case: production, not built.

## 4. Stakeholder concerns and BOUND's answer

| Concern | Answer | Honest caveat |
|---|---|---|
| "Can a leak be traced to a person?" | Yes, to the **signing session** via ledger. | Signature proves key possession, not human action. |
| "Can the admin delete the record?" | In LAN mode, no — node keys are on separate devices. | Local mode keys are colocated (prototype). |
| "Does it need internet?" | No. Fully offline. | Plain HTTP on the LAN is intentional; LAN is the boundary. |
| "Will recipients notice?" | No visible change; text stays selectable. | Embedded images are re-encoded. |
| "Does it survive a camera photo?" | Not guaranteed. | Stated openly; not a claimed capability. |
| "Is it quantum-safe?" | Key exchange and signatures are NIST PQC. | Symmetric side is AES-256 (quantum-resistant classically). |

## 5. Who this is NOT for

- Consumers expecting DRM-locked media.
- Anyone needing **prevention** rather than **attribution**.
- Anyone needing guaranteed attribution after heavy lossy transformation.
- Anyone needing legally certified non-repudiation today (needs client-side signing + audit).

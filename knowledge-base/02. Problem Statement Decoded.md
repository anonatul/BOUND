This document decodes the PS into requirements and maps each one to what the prototype
actually implements. It is the contract against which the demo must be judged.

---

## 1. The PS in its own words

> The problem is that when the same sensitive document is given to multiple people, a leaked
> copy cannot normally tell us who leaked it. Our solution is to give every decrypted copy a
> **unique invisible forensic fingerprint**. … The system is designed for **forensic
> attribution after a leak**, not for completely preventing leaks.

> **Final concept:** "We don't try to stop a trusted recipient from leaking a document. We
> make every decryption produce a unique, invisible forensic fingerprint and cryptographically
> record that decryption event in an offline distributed ledger. When a copy leaks, the
> fingerprint can be extracted and matched with the signed ledger record to determine which
> recipient's decryption session produced that copy."

The PS itself mandates honesty about limits (§19 "What the System Does NOT Guarantee" and
§20 "Main Technical Risks"). Any pitch that hides those is off-spec.

## 3. The PS's three "most important demos"

The PS §21 names exactly these, and the prototype implements each:

1. **Two recipients, identical-looking documents, different fingerprints, leak one → identify recipient/session.**
   → `/api/test/end-to-end`, `test_crypto.py::test_complete_end_to_end_attribution`
2. **Modify the audit record → verification fails.**
   → `/api/test/ledger-tampering`, `test_ledger_v2.py::test_checkpoint_tamper_detected`
3. **Modify the signed event → ML-DSA verification fails.**
   → `/api/test/signature-tampering`, `test_crypto.py::test_mldsa_modified_rejection`

✅ **VALIDATED** — all three have passing automated tests.

## 4. Where the implementation makes a deliberate choice

The PS §12 says: *"If the judges strictly expect a real DLT/blockchain, a permissioned
blockchain such as Hyperledger Fabric is safer than calling a simple database a blockchain."*

- 🟣 **DECISION:** BOUND does **not** ship Hyperledger Fabric. It ships a **custom
  replicated signed append-only ledger** with per-node ML-DSA signatures, Merkle
  checkpoints, quorum, divergence detection and peer repair.
- **Why:** it runs fully offline with zero extra infrastructure, and the "no single admin"
  property is achieved structurally by separating node keys onto real devices in LAN mode.
- **How to defend it:** never call it a "blockchain consensus network". Call it a
  **tamper-evident, quorum-replicated, independently-signed ledger**. See `23` for the
  exact wording.

| PS expectation | Reality | Label |

| "survives screenshot / photograph" | not guaranteed; rasterize mode helps but is not claimed to pass a camera test | 🔴 not claimed |
| "a real DLT" | custom signed ledger, not Fabric/CometBFT | 🟣 decision |

## 6. The PS requirement checklists (verbatim expectations)

**Expected solution (§ from PS "What the System Guarantees"):**

- ✅ A different forensic fingerprint for each decryption session.
- ✅ Cryptographic binding between the decryption event and the recipient's signing key.
- ✅ Detection of unauthorized changes to ledger records.
- ✅ Offline operation.
- ✅ Post-quantum key establishment (ML-KEM).
- ✅ Post-quantum signatures (ML-DSA).
- 🟡 Forensic matching **when the leaked artifact retains a recoverable watermark**.

**Explicit non-guarantees (PS §19):** never deny, never hide.

---

## 7. Bottom line

BOUND implements the PS's recommended "simpler prototype fallback" (multi-node append-only
hash-chain/Merkle ledger) rather than the preferred "investigate" option (Hyperledger
Fabric). Every concrete requirement in the PS has code and a passing test behind it; the
deliberately partial items are the endpoint-hardening and non-repudiation items, which the
PS itself flags as future work.

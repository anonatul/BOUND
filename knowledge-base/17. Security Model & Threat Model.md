## 1. Assets

| Asset | Why it matters |
|---|---|
| Document plaintext | the secret being protected |
| AES document key | unlocks the plaintext |
| Recipient ML-DSA private key | signs decryption events (non-repudiation) |
| Node ML-DSA private keys | make ledger history unforgeable |
| Ledger history | the evidence used for attribution |
| Watermark ID ↔ recipient mapping | the link between artifact and person |

## 2. Trust boundaries

1. **Recipient endpoint** — NOT trusted to protect plaintext (recipient sees it).
2. **Coordinator process** — trusted to route, but NOT trusted with node keys in LAN mode.
3. **Witness devices** — trusted as independent signers; each holds its own key.
4. **Isolated LAN** — the security boundary for LAN transport (plain HTTP is intentional).
5. **Investigator** — trusted to run verification honestly; can re-verify independently.

## 3. Threat model (in scope)

| # | Adversary | Goal | BOUND's defence | Status |
|---|---|---|---|---|
| T1 | Privileged operator / compromised coordinator files | alter or delete audit records | per-node ML-DSA signatures + Merkle checkpoints; quorum; LAN keys on separate devices | ✅ local-design + tested; LAN by design |
| T2 | Recipient leaks a copy and denies it | avoid attribution | unique session watermark + signed event + ledger mapping | ✅ tested |
| T3 | Investigator receives a leaked artifact | identify source | extraction → ledger match → signature + quorum verification | ✅ tested |
| T4 | Attacker forges a watermark ID | frame an innocent recipient | ID not in ledger → `NO_LEDGER_MATCH` | ✅ tested (`fake-watermark`) |
| T5 | Attacker edits the signed event | change recipient/session | ML-DSA verification fails | ✅ tested |
| T6 | Attacker edits one node's file | hide a record | `verify_ledger_node` flags it; attribution survives via quorum | ✅ tested |
| T7 | Attacker rewrites all four local files and recomputes hashes | forge history | node signatures cannot be forged without node keys | ✅ tested |
| T8 | Quantum adversary records ciphertext | decrypt later | ML-KEM-768 key establishment; ML-DSA signatures | ✅ by construction |
| T9 | Unauthorized user tries to decrypt | read the document | authorization check + KEM: without the wrapped key, AES-GCM fails | ✅ tested |

## 4. Out of scope (documented non-defences)

| # | Attack | Why it is out of scope |
|---|---|---|
| O1 | Recipient photographs the screen | no software-only fix; PS says so |
| O2 | Recipient modifies the viewer / extracts plaintext | endpoint is not trusted |
| O3 | Watermark removal / heavy re-processing | robust against selected transforms only |
| O4 | Stolen recipient private key | signature then proves key possession, not the legitimate owner |
| O5 | Compromised majority of ledger nodes | trust model assumes a non-compromised majority |
| O6 | Side channels, memory scraping after unlock | server holds decrypted keys for 30 min |
| O7 | Malicious LAN device joining | gated by optional `BOUND_ENROLL_TOKEN`; key pinned on join; LAN is the boundary |
| O8 | DoS / rate limiting | not implemented |

## 6. Cryptographic strength notes

| Question | Answer |
|---|---|
| "Is 128-bit watermark enough?" | Yes: guessing a valid ID is 2¹²⁸, and a guessed ID fails ledger lookup. |
| "Why ML-KEM-768 / ML-DSA-65?" | NIST Level 3 balanced size/performance; 1024/87 available. |
| "Can you brute-force the session ID?" | `SES-` is only 24 bits, but it is never used alone; the 128-bit nonce and doc hash feed the watermark. |
| "What if two sessions collide?" | Different nonces make identical IDs astronomically unlikely; both sessions would be in the ledger anyway. |
| "Can the coordinator mint a fake event?" | It can propose, but every node validates chain continuity and each node signs; without node keys it cannot create quorum-valid history. |

## 7. Honest weaknesses (must be stated, never hidden)

1. **Server-side signing** after unlock weakens non-repudiation: the recipient's key is in
   server memory. Client-side signing or a hardware key is required for true non-repudiation.
2. **Local mode colocated node keys:** an attacker with file access *and* the node key files
   can forge. LAN mode exists precisely to remove this.
3. **Legacy demo accounts** (`ALICE`/`BOB`) keep plaintext keys for compatibility.
4. **Container fallback protects only the wrapper.**
5. **No fuzzing, no formal audit, no rate limiting, prototype file storage.**
6. **CORS `*` and localStorage tokens** are prototype choices.
7. **Plain HTTP on the LAN** — acceptable only because the network is physically isolated.

## 8. The sentence to memorise

> **"BOUND makes unauthorized modification of the audit record detectable and prevents a
> single administrator or compromised node from silently rewriting history, under its stated
> trust model. It does not prevent leaks, does not stop a camera, and a signature proves key
> possession — not human action."**

Everything else in the pitch is safe if this sentence stays true.

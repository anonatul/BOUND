## 1. Project Name

**BOUND**

The repository and product are named **BOUND**. The README title is:

> **BOUND — Offline Post-Quantum Forensic Document Attribution**

There is **no official backronym** for BOUND in the code or docs. Do not invent one on
stage unless the team agrees. The name is used as the product brand ("BOUND Documents" in
the UI).

---

## 2. One-Line Definition

> **BOUND is an offline, post-quantum document distribution and forensic attribution system:
> every decrypted copy carries a unique invisible session watermark, every decryption is
> signed and committed to a tamper-evident multi-node ledger, and a leaked copy can be
> traced back to the recipient and exact session.**

---

## 3. Core Mission

Make it possible to answer, **after a leak, with cryptographic evidence**:

> **Which authorized recipient — and which specific decryption session — produced this leaked copy?**

BOUND focuses on the transition:

```text
Encrypted document
      ↓
Authorized recipient decrypts
      ↓
Fresh session + nonce
      ↓
Unique invisible watermark embedded
      ↓
Decryption event signed (ML-DSA)
      ↓
Committed to offline signed ledger
      ↓
Document leaks
      ↓
Fingerprint extracted → ledger matched → signature verified
      ↓
Recipient + session identified
```

BOUND is therefore a **forensic attribution system**, not a leak-prevention / DRM system.

---

## 4. Core Problem

When the same confidential document is distributed to many people:

- **Access logs** can say "Alice downloaded at 10:30", but a privileged administrator can
  alter or delete logs.
- **Static watermarks** ("CONFIDENTIAL — COMPANY XYZ") are identical for every recipient,
  so they identify the document but not the leaker.
- **Screenshots / camera photos** bypass any screen-level control.
- **A leaked file** usually arrives with no reliable, cryptographically verifiable link to a
  person.

BOUND addresses the gap between "we know who was *allowed* to read it" and
"we can *prove* who produced this leaked artifact".

---

## 5. What BOUND Does

1. Encrypts a document once with AES-256-GCM.
2. Protects the AES key for each authorized recipient with ML-KEM-768 (post-quantum KEM).
3. On decryption, generates a fresh session ID + random nonce.
4. Derives a **128-bit opaque watermark ID** from
   `SHA-256(document_hash | recipient_id | session_id | nonce)`.
5. Embeds that watermark invisibly, using a format-specific channel:
   PDF, image, text-like, OOXML, or a generic ZIP container fallback.
6. Signs the canonical decryption event with the recipient's **ML-DSA-65** key.
7. Commits the signed event to a **multi-node ledger**, where each node independently
   signs the entry and a Merkle checkpoint; commits require a quorum.
8. On a leak, extracts the watermark from the leaked artifact, looks it up in the ledger,
   verifies the recipient signature and node quorum, and returns a verifiable attribution.

---

## 6. What BOUND Is NOT

- Not a DRM product that prevents copying.
- Not a system that can stop a phone camera photographing a screen.
- Not a claim that watermarks are unremovable.
- Not a public blockchain.
- Not a cloud KMS.
- Not a production-hardened, independently audited cryptographic system.
- Not an AI/ML project — there is **no machine learning** anywhere in the prototype.
  (This matters: do not pitch "AI" for BOUND.)

---

## 7. The Five Pillars (the actual idea)

BOUND is not a new algorithm. It is the **composition** of five existing technologies into
one offline chain of evidence:

```text
Post-Quantum Encryption        (ML-KEM-768 + AES-256-GCM)
          +
Session-Specific Watermark     (128-bit, format-aware, invisible)
          +
Post-Quantum Signature         (ML-DSA-65 over the canonical event)
          +
Offline Permissioned Ledger    (per-node ML-DSA signatures, Merkle checkpoints, quorum)
          +
Forensic Verification          (blind extraction → ledger match → signature/quorum check)
```

- 🟣 **DECISION:** The defensible innovation is the **integration and the chain of
  evidence**, exactly as the PS says. Each individual primitive is standard.

## 8. Core Objects

| Object | Meaning |
|---|---|
| **Document** | `DOC-XXX`, an AES-GCM ciphertext plus one ML-KEM-wrapped key per recipient. |
| **Recipient** | An account `[A-Z0-9_]{3,24}` with an ML-KEM-768 and an ML-DSA-65 keypair. |
| **Session** | `SES-` + 6 hex chars, generated fresh at each decryption. |
| **Watermark ID** | `WM-` + 26 base32 chars (128-bit). Opaque; no identity inside. |
| **Decryption Event** | Canonical JSON record of one decryption, signed by the recipient. |
| **Ledger Entry** | The event + recipient signature + chain hashes + per-node signature. |
| **Checkpoint** | Signed Merkle root over all entry hashes for a node. |

## 9. Core Design Principles

### 9.1 Attribution, not prevention
The system assumes a leak can happen. It optimizes for **provable identification afterwards**.

### 9.2 Opaque fingerprints
The watermark ID contains **no plaintext identity**. The mapping to a recipient lives only in
the ledger. A leaked file alone reveals nothing unless you have the ledger.

### 9.3 Evidence over assumptions
Every strong claim must be tagged ✅ Validated / 🟡 Assumption / 🔵 Unverified / 🔴 Rejected.

### 9.4 Offline by construction
No internet, no cloud KMS, no public blockchain, no TEE. The air-gapped LAN is the trust boundary.

### 9.5 Honest limitations
Screenshot/photo/print-scan removal, endpoint control, key compromise and server-side
signing are stated openly (see `18` and `17`).

### 9.6 No single admin
In LAN mode each node's ML-DSA private key is generated on and never leaves its own
device, so a privileged coordinator cannot forge a consistent rewrite of history.

## 10. Current MVP

The MVP proves the whole loop with **real cryptography and real watermarking**:

```text
Encrypt (any file type)
  → Give to ALICE and BOB
  → Each decrypts (different watermark)
  → Each decryption signed + committed to 4-node ledger (quorum 3/4)
  → Leak Alice's copy
  → Verify → "Recipient ALICE, session SES-XXXXXX, signature VALID, quorum VALID"
  → Tamper the ledger → verification fails
```

**Measured state (2026-09-27):** `uv run pytest backend/tests -q` → **110 passed in ~11 s**.

## 11. Critical Claims That Require Care

| Claim | Status |
|---|---|
| Real ML-KEM-768 / ML-DSA-65 / AES-256-GCM in code | ✅ VALIDATED |
| Per-session watermarks differ and round-trip | ✅ VALIDATED |
| Multi-node signing + Merkle checkpoints + quorum | ✅ VALIDATED |
| Admin without node keys cannot forge history | ✅ VALIDATED (local model) |
| Watermark survives print/scan/screenshot | 🔴 REJECTED as a blanket claim |
| Signature proves a human personally acted | 🔴 REJECTED (proves key possession) |
| Full non-repudiation (client-side signing) | 🔵 UNVERIFIED / not implemented |
| "Immutable" absolute ledger | 🔴 REJECTED (tamper-evident, not immutable) |
| Blockchain-grade BFT consensus | 🔴 REJECTED (replicated signed structure) |

## 12. Golden Rule

> **If BOUND cannot prove a claim, BOUND must not pitch it as a fact.**

The goal is not to sound futuristic. The goal is to be **technically defensible under
aggressive SIH judging** — and the README's "Honest Limitations" section already models
this discipline.
